# 이미 도착한 좌표를 고르는 이유: 같은 입력 재생

2026-10-18 · MC-056. [M 실제 검증](PROPOSAL_LIVE.md)의 저장 입력만 사용했다. Minecraft 접속·월드 변경·본실험·런타임 정책 수정은 없다. 로컬 강제 행동이나 목적지 삭제도 없다.

## 어느 단계에서 막혔나

완료된 목적지 검토162건을 요청ID로 연결했다. 철회153건 모두 이미 도착 반경2 안의 제안이었다. **153건 모두 선택된 그룹 안에는 반경 밖 좌표도 남아 있었다.** 그룹이 가까운 좌표만 남기도록 잘못 잘랐다는 가설은 이 기록에서 배제된다. 반경 밖은 경로가 보장된다는 뜻이 아니다.

최종 좌표가 특정 목록 위치에 고정된 것도 아니다. Bob은 그룹을 섞으면 그룹24의 세 번째에서 그룹6의 네 번째로 옮겨간 같은 실제 좌표를 계속 골랐다. 이는 단순 첫 항목 선택보다 좌표/상태 의미에 연결된 선호와 맞는다. 모델의 내부 사고 이유는 API 응답으로 직접 관측할 수 없다.

## 비교 방법

Alice/Bob 철회 입력을 각각 첫·중간·마지막에서 고르고 Alice의 성공 대조1개를 더한7관측, 조건별2반복이다. 실패 편향 표본이며 일반 성공률을 추정하지 않는다. 원본 모델 응답을 로컬에서 재생해 재구성한 기본 조건의 **질문·상태·전송 문자열이 각 단계 원본과 완전히 일치**하는지 먼저 확인했다. 이전 부분 도메인 재생 오류를 되풀이하지 않도록 전체108~502개 좌표를 root 질문에서 복원했다.

조건 실행 순서를 교차했고 관측·계획·기억·철회 권한은 고정했다. 그룹 변경은 거리와 무관한 고정 시드 순열이다. 좌표 집합은 같지만 그룹 구성·목록 순서·선택지 ID는 함께 바뀌므로 이 세 요소를 서로 분리한 실험은 아니다. 절대좌표 조건은 질문의 상대좌표 압축만 일반 x/y/z JSON으로 바꾸며 상태는 그대로다.

| 전체 그룹→좌표→최종 검토 | 반경 밖 선택/14 | 철회/14 |
|---|---:|---:|
| 기존 |2|12|
| 질문 좌표를 절대좌표로 표기 |3|11|
| 그룹 구성/순서 섞기 |4|10|
| 둘 다 변경 |2|12|

모든 조건의 모든 선택 그룹에 반경 밖 좌표가 남았다. 큰 단일 원인으로 압축 표기나 그룹 구성을 지목할 근거는 부족하다. 특히 Bob의6회 판단은 네 조건 모두 같은 이미 도착한 좌표 제안→철회였다. 개선된 기존 성공 대조와 실패 사례를 구분해 보존한다.

## 마지막 좌표 선택만 고정한 추가 비교

그룹을 원본 그대로 고정하고 같은 후보와 계획에서 질문했다. 두 비교 모두 각 조건14회다.

- 각 후보의 거리 수치·반경2·실행 결과를 추가: 반경 밖 제안 **2→2**. 기존 설명을 보존했으며 거리 계산 결과만 더했다. 단순 기하 정보 누락이라는 설명은 지지되지 않는다.
- 상태의 `alreadyWithinArrivalRadius` 배열을 `meaning + coordinates` 객체로 표시하고 “이미 도착했으므로 이동 실행이 시작되지 않는 사실 목록이며 추천 목록이 아니다”라고 명시: **2→6**. 좌표·원래 의미를 모두 유지하고 역변환 일치를 확인했다. Bob 중·후반2관측이 각각2반복 모두 개선됐고 Alice와 Bob 초반은 그대로였다.

두 번째 변화는 객체 구조와 의미 설명을 함께 바꾼 것으로, 단어 하나의 효과를 분리한 실험은 아니다. 다만 같은 사실도 부정적 실행 결과라는 역할을 얼마나 분명히 드러내는지에 선택이 민감하다는 증거다. 아직 “목록을 추천으로 오해했다”는 내부 원인을 확정하지는 않는다.

## 전체 절차에서 재확인

같은7관측을 다시2반복하여 기본 조건과 목록 역할 표시만 비교했다. 그룹/좌표/최종 검토를 모두 다시 호출했으며 전체 좌표와 질문 지시문은 유지했다.

| 조건 | 반경 밖 선택/14 | 철회/14 |
|---|---:|---:|
| 기존 |2|12|
| 이미 도착한 목록의 실행 의미 표시 |7|7|

Bob 중·후반2관측은4회 모두 개선, Alice 중반1회가 추가로 개선됐다. 성공 대조2회는 유지됐다. 나머지7회는 여전히 도착 반경 안 제안→철회다. 실행 결과를 분명히 표현하면 일부 일관성이 회복되지만 전체 판단 문제를 해결하지는 못했다.

## 결론과 다음 단계

**확인된 동작 원인:** 제안 단계가 무동작 목적지를 고르고 최종 검토는 이를 거절한다. 원본과 동일한 입력에서 재현됐고, 계획을 기다리거나 네트워크가 느려서 생긴 현상이 아니다. 선택된 그룹에 대안도 있었다.

**지지되는 원인 가설:** `alreadyWithinArrivalRadius`라는 특수 목록의 부정적 실행 의미를 제안 단계가 충분히 활용하지 못한다. 역할을 명시한 표현에 반응했으므로 입력 계약/표현과 모델 판단의 상호작용을 개선할 여지가 있다. 목록을 실제 추천으로 오해했는지, 반복된 좌표가 두드러져 선택했는지, 추가 설명이 단순 주의 환기를 했는지는 이번 비교로 분리되지 않는다. JEV 일반 판단력이 부족하다는 결론도 내리지 않는다.

**이번에 지지되지 않은 단독 원인:** 후보 누락·잘못된 그룹 제한·고정 첫 항목·상대좌표만의 문제·거리 수치 누락. 작은 실패 편향 표본이므로 다른 상태에서 이 문제들이 생기지 않는다는 뜻은 아니다.

다음은 관측 사실에 실행 효과를 연결하는 표현을 더 넓은 저장 입력에서 확인하는 것이다. 후보 삭제·강제 이동·수동 생존 규칙을 추가하지 않는다. 남은 실패에서 목표의 보수성, 제안/최종 검토 질문의 불일치, 효과 표시 방식을 각각 분리할 필요가 있다. 실제 이동 성공·idle 개선은 아직 측정하지 않았으며, 이번 변경은 재생 도구에만 존재한다.

## 재현·비용

- `scripts/destination-factor-replay.ts --input=<events.jsonl>`: 원본 일치/전체 도메인 감사. `--with-api`를 붙이면 네 조건 비교, `--arrival-label`을 추가하면 목록 역할 표시 비교.
- `scripts/destination-leaf-replay.ts --input=<events.jsonl> --audit=<factor-audit.json>`: 원본 leaf 고정 감사. `--with-api`로 거리/효과 표시, `--arrival-label`로 목록 역할 표시 비교.
- 유료 호출은 `--authorized-total-usd=<budget>`도 지정하며 공유 원장을 사용한다. 각 도구 실행은 비용/호출 상한이 있고 서버 접속은 없다. 원본 로그·좌표·대화·API 응답은 비공개다.
- 타입 검사 및7개 전체 원본 경로/7개 leaf의 전송 내용 일치 검사 통과. 초기 도구 구현에서 JSON 키 순서 차이와 타입 선언 오류를 수정한 뒤 유료 호출을 시작했다. 운영 소스는 바꾸지 않았다.
- 네 조건$0.110922840 + leaf 기하$0.017017560 + leaf 목록 역할$0.016801260 + 전체 목록 역할$0.054129432 = **$0.198871092**, JEV308회. 모두 정상 응답. 서버 실행과 본실험은 없었다.
