# JEV Minecraft 봇과의 시스템 비교

기준일: 2026-10-18. 비교 대상은 [rmalde/minecraft-agent](https://github.com/rmalde/minecraft-agent)의 커밋 `78b40ed59514e5e2abde33a05ce398ecb2c39e05`이며, 특히 공개된 **nether-agent의 지정 경로 완주 방식**을 기준으로 한다. 저장소의 다른 실행 모드까지 모두 같은 구조라고 일반화하지 않는다.

우리 프로젝트의 방향은 **목표·행동 인자·경험 갱신을 모델에 맡기고, 실제 결과와 판단 사이의 단절을 추적하는 지속형 다중 봇**이다. 상대보다 게임을 잘하거나 더 빠르게 수행한다는 주장은 아니다. 지금 강조할 수 있는 것은 구현한 제어·관측·기억 구조와 실패를 검증하는 과정이다.

## 한눈에 보는 구조

```text
비교 대상(nether-agent)
지정 공략·준비물·월드 경로 → 코드가 단계와 완성 행동 후보 구성
                         + Astra 비동기 계획
                         → JEV가 후보 하나 선택 → 실행 완료 → 다음 선택

우리 v2
게임 설명 + 선택적 요청 + 관측·기억 → 장기 LLM 목표 / 중기 LLM 작업 의도
                                   → JEV 행동 선택 → 조건부 인자 선택
                                   → 로컬 실행, 실행 중에도 유지·전환 판단
선택·미실행·실행 결과·상태 변화 → 목표 재검토 / LLM 경험 지침 갱신
대화 LLM은 별도로 동작하며 목표·약속 기억과 연결
```

두 시스템 모두 Mineflayer와 사전 구현한 동작을 사용한다. 모두 생성 모델과 JEV를 결합하며, 비교 대상에도 비동기 계획이 있다. 따라서 이 조합 자체나 비동기 호출 자체를 독창성으로 내세우지 않는다.

## 시스템 차이와 장단점

| 기준 | 비교 대상: 지정 경로 완주 | 우리 v2 | 이 차이의 이점과 비용 |
|---|---|---|---|
| 목표 | 공략 단계·준비물·주요 경로를 코드와 프롬프트에 구체화 | 게임 설명과 요청을 구분하고 LLM이 목표·근거·완료/보류 상태 관리 | 목표 변경을 다룰 여지가 크지만, 목표 품질과 완료 판단까지 실패할 수 있음 |
| JEV의 선택 | 코드가 대상·수량·실행 함수를 붙인 완성 후보 중 하나 선택 | 행동을 고른 뒤 관측된 도메인에서 대상·좌표·아이템 등 인자 선택 | 더 많은 선택을 모델에 위임하나, 행동과 인자가 불일치할 수 있음 |
| 로컬 판단 | 단계 전환, 준비물 조건, 경로, 일부 후보 우선순위·유지 규칙 | 스킬·선택 도메인·물리 검증·경로 탐색·실행 취소를 코드가 담당 | 과업별 공략 정책은 줄였지만 로컬 판단이 없는 시스템은 아님 |
| 실행과 계획 | Astra 계획은 비동기. 주 JEV 루프는 선택한 실행을 기다림. 별도 전투 반사 제어 존재 | 실행 중 JEV 재판단, 중기·장기·대화·경험 검토를 분리 | 진행 중 계획·대화가 가능하지만 늦은 응답과 실행 충돌 관리가 필요 |
| 환경 정보 | 구조화 상태와 로드된 청크 정보, 지정 경로의 사전 월드 정보 활용 | 기하학적 시야·가림 검사, 자기 상태와 과거 관측 장소 구분 | 관측 제한 아래 기억을 평가할 수 있으나 누락·오래된 정보가 행동을 막을 수 있음 |
| 기억 | 살펴본 경로에서는 최근 기록·계획·공략 상태를 활용 | 경험, LLM 지침의 근거·반례, 장소·사회적 기억, 목표를 분리해 저장 | 경험 기반 변경을 추적 가능. 지침의 유용성·검색 누락·장기 규모는 미검증 |
| 대화·협동 | 해당 완주 경로는 단일 봇 과업 중심 | 봇별 기억, 별명·메시지 분류, 대화·약속과 목표 연결 | 다중 봇 협동을 연구할 기반은 있지만 대화가 실제 협동 성과를 보장하지 않음 |
| 사망 | 해당 실행은 사망 시 중단 | 리스폰 후 회수·준비·보류·포기 판단과 이후 결과 갱신 | 실패 후 지속 가능성을 다루지만 위험 지역 회수 능력은 추가 검증 필요 |
| 검증의 중심 | 지정 조건에서 완주 시간과 경로 수행 | 기능 성공, 판단/인자 불일치, 공백, 목표 변화, 비용과 실제 성과 | 실패 원인을 자세히 볼 수 있으나 명확한 종착점이 없어 평가 설계가 어려움 |

## 자유도는 어디까지인가

비교 대상도 실제 모델 판단을 사용한다. 다만 nether 경로의 특정 준비 단계에서는 정해진 침대·상자·경유지 등을 코드가 선택지로 만들고, 조건에 따라 선택지가 하나로 좁아지기도 한다. 완성된 행동 중 고르므로 행동과 인자의 불일치가 생길 여지가 작고 공략 효율을 확보하기 쉽다. 다른 월드·목표로 옮기려면 해당 전제와 정책을 다시 점검해야 한다.

우리도 임의의 모든 행동을 생성하는 것은 아니다. 17개 스킬, 관측에 근거한 유한한 인자 도메인, 실행 시간·거리·물리 제약은 코드가 정한다. 그 안에서 무엇을 하고 어디를 대상으로 할지는 JEV에 맡긴다. 기본 조작부터 배우는 버전은 아직 설계 단계다. **선택권 확대와 선택 능력 향상은 별개**이며, 현재는 바로 이 경계가 주요 병목이다.

## 지금 주장할 수 있는 것과 없는 것

- **구현된 것:** 역할별 비동기 제어, 실행 소유권·오래된 응답 검사, 제한된 관측, 목표/기억 분리, 근거 있는 지침 갱신, 결과 계측. 제한된 서버에서 개별 기능과 병렬 동작을 확인했다.
- **아직 입증하지 못한 것:** 안정적인 장기 생존, 자발적이고 생산적인 협동, 기억이 실제 성능을 높인다는 인과 효과, 비교 대상 대비 우수성.
- **현재 약점:** 최근 120초 검증의 평균 무실행 비율은 95.11%였다. API 오류가 없어도 행동·인자 선택 미완결과 이미 도착한 위치 선택이 남았다. [실제 검증](JEV_ARGUMENT_REPLAY.md)
- **원인 분리 중:** 같은 입력에서 행동을 고정한 18회 판단은 기존 방식의 인자 완성 7회·스냅샷 검증 통과 7회에서, 조건부 인자 질문의 none 제거 시 18회·12회로 달라졌다. 실행 성공이나 실제 공백 감소를 측정한 결과는 아니다. 운영 정책도 아직 바꾸지 않았다. [재생 비교와 한계](JEV_CHOICE_COMPARISON.md)

비교 대상의 8분 43.3초 완주는 작성자 보고다. Peaceful, 사전 조사한 월드·보급·경로와 활성화된 엔드 포털 등의 조건이 명시되어 있다. 독립 재현하지 않았으며 우리 생존 파일럿과 직접 비교할 수 없다. 원본 녹화·월드·실행 증거 일부는 저장소에 포함되지 않는다. [보고 조건](https://github.com/rmalde/minecraft-agent/blob/78b40ed59514e5e2abde33a05ce398ecb2c39e05/README.md)

## 포트폴리오에서 강조할 내용

> 생성 모델이 목표·대화·경험 지침을 갱신하고 JEV가 행동과 인자를 선택하는 Minecraft 다중 봇 시스템을 구현했다. 관측·기억·실행의 경계를 분리하고, 판단 지연·선택 불일치·실제 상태 변화를 기록해 자율 행동이 멈추는 원인을 재생 검증했다.

핵심 기여는 “AI 봇을 연결했다”를 넘어 **실행 가능한 선택의 계약, 기억과 목표의 갱신, 실패를 재현하고 검증하는 도구**를 만든 데 있다. 이는 엔지니어링 기여의 설명이며, 학술적 신규성은 더 넓은 선행 연구 검토와 통제 실험이 있어야 주장할 수 있다. 문제·시도·검증 한계는 [시행착오 기록](ENGINEERING_LOG.md)에 계속 남긴다.

## 다음 비교에서 확인할 질문

1. 같은 관측·실행기·모델·초기 조건·예산에서 완성 후보 선택과 행동/인자 선택은 유용한 성과·공백·비용을 어떻게 바꾸는가?
2. 기억을 읽거나 갱신하는 경우가 없는 경우보다 실패 반복과 목표 완수를 개선하는가? 근거 없는 지침이 오히려 악화시키지는 않는가?
3. 두 봇의 대화가 실제 분담·전달·공동 작업으로 이어지는가? 대화 횟수 대신 실행 결과로 측정한다.

이는 평가 계획이며 이미 수행한 결과가 아니다. 현재 기록은 통제된 상대 구현과의 성능 비교가 아니다.
