# v2.5 작업 절차

기존 `WORKFLOW_MODE=direct`를 보존하고 `procedural`을 추가했습니다. 액션을 추가하기보다 기존 실행기를 연결해 작업 사이의 세부 선택 호출을 줄이는 방식입니다. 짧은 서버 검증에서 수집·제작 정산과 전투 후 복귀를 확인했습니다. 준비된 양·원목에서 재료를 확보해 침대1개를 만들었지만 반복 중단·철회는 남아 있습니다.

| 구성 | 결정하는 내용 |
|---|---|
| LLM | 작업 목적·자원 종류·허용 구역·순서·완료 수량·실행 상한 |
| JEV | 상황 변화에 따른 행동 유지·전환·작업 복귀, 대화 전달·계획 재검토 요청 |
| 로컬 | 위임 범위 내 대상 연결·재료 산술·순차 실행·실제 결과 확인 |

JEV는 작업 중 상황에 대응합니다. 피격·허기·주야간·환경·대상 변화와 다른 플레이어의 요청을 관측·결과·대화에서 읽고, 현재 행동이 여전히 적절한지 판단합니다. 변화 자체로 중단을 강제하지 않으며 필요하면 기존 행동과 인자를 골라 대응합니다. 중기 작업이나 장기 목표를 고칠 필요가 있으면 LLM 검토를 요청하고, 대화는 별도로 전달합니다.

`continue`는 현재 동작을 다음 판단까지 유지하며 작업 전체를 끝내겠다는 약속이 아닙니다. 다른 행동으로 전환할 때 `stop`을 먼저 고를 필요가 없습니다. 전환 후에도 진행 위치를 보존하고, JEV가 `resume_procedure`를 선택하면 현재 관측·소지량으로 남은 작업을 재개합니다. 개별 `mine`·`craft`는 그 동작만 실행하고, `resume_procedure`는 남은 절차를 이어 실행한다는 차이를 선택지에 명시합니다. 새 계획의 도착이나 상황 해소만으로 작업을 교체·재개하지 않습니다. 이들은 실행 제어이며 새로운 게임 동작이 아닙니다.

## 현재 지원

절차는 최대6단계이며 `mine` 수집 단계와 `craft` 제작 단계를 연결합니다. 수집은 LLM이 지정한 자원·중심·반경(최대12블록) 안에서 현재 보이거나 최근에 관측한 같은 이름의 드롭을 먼저 줍고, 없으면 가까운 같은 이름의 블록을 채굴합니다. 동률은 좌표/ID로 결정하며 현재 손에 든 도구를 유지합니다. 이 규칙은 **명시적으로 로컬에 위임한 선택**이며 JEV가 개별 대상을 골랐다고 기록하지 않습니다.

제작은 LLM이 정한 출력·재료 종류와 봇이 해금한 제작법으로 계산합니다. `targetCount`는 최종 소지 수량이며 `materialsFor`는 뒤 제작 단계의 재료 요구량을 참조합니다. 예를 들어 판자8개가 목표이고 원목1개·판자3개를 갖고 있으면 제작2회, 원목1개 추가가 필요합니다. 제작 시에도 계산에 사용한 재료 변형을 그대로 사용합니다. 목표 수량을 만들 재료가 없으면 앞선 수집 단계를 LLM이 정해야 합니다. 제작마다 서버 인벤토리를 재동기화하고 커서·제작 칸의 물건을 정리한 뒤 실제 증가량을 확인합니다. 취소 후에도 진행 중이던 거래의 정산은 마칩니다.

블록 파괴·드롭 관측·인벤토리 증가는 분리합니다. 실제 소지량으로 단계를 완료하며, 이후 제작으로 재료를 소비해도 완료한 수집 단계를 다시 열지 않습니다. 실행 기록은 시작 당시 작업 ID와 단계 ID를 유지합니다.

## 경계와 기록

- 블록명과 얻을 아이템명이 같은 수집만 지원합니다. `mine`은 임의의 아이템 확보 명령이 아니며 동물 공격·털 깎기를 실행하지 않습니다. 동물 상호작용이 필요한 선행 작업은 일반 액션으로 계획하고, 실제 획득을 확인한 뒤 남은 제작 절차를 갱신합니다. 광석의 다른 드롭, 자동 도구 선택, 재귀적 재료 제작, 화로 절차는 미지원입니다.
- 가려진 블록·과거 기억만 있는 블록은 자동 수집 대상이 아닙니다. 절차 구역은 JEV의254개 후보 제한과 별개이며 모델에 명시합니다.
- 미해금/모호한 제작법, 부족한 재료, 대상 소진, 실패·미획득은 중단 사유로 반환합니다. 다른 자원·구역·행동을 자동으로 대신 고르지 않습니다.
- 시작할 수 없는 절차는 부족분·거절 이유를 LLM과 JEV에 전달합니다. 같은 실패 절차는 관련 재료·관측이 그대로일 때 새 작업 ID로 재시작하지 않으며, 단계 이름만 바꾸어도 동일하게 취급합니다. 다른 행동을 자동 선택하지 않습니다.
- 드롭 기억은 현재 가시성과 분리해 최대64개·120초 보관합니다. 가려진 엔티티의 현재 좌표를 갱신하지 않고 마지막 관측 위치에 접근해 재확인합니다. 직접 주운 서버 이벤트는 해당 기억을 제거합니다. 위치 기억이나 엔티티 소멸만으로 획득을 인정하지 않습니다.
- 단계당 무제한 재시도 없이 전체 행동 횟수·시간 상한을 지킵니다. 취소 시 관측된 획득은 보존하며 재개 선택 전에는 남은 절차를 실행하지 않습니다. 재개해도 작업 ID·완료 단계·누적 시도·원래 시간 상한을 유지합니다. 사망·재접속·사용자 목표 변경은 기존 절차의 재개를 무효화합니다.
- `workflow_configuration`, `procedure_started/resumed/action/steps_completed/completed/blocked/suspended`를 기록합니다. 개별 액션은 `source=procedure`, `selectorKind=local_procedure`로 JEV 선택과 구분합니다. 이 기록의 `confidence=1`은 기존 형식의 기계적 값이며 모델 신뢰도가 아닙니다.

사용자의 요청과 해금된 지원 제작법의 보유량·1회 부족분·가능 횟수를 첫 JEV 판단부터 전달합니다. 인자 선택 중 `revise`로 철회할 수 있고, 완료된 인자는 추가 승인 없이 실행합니다. 제작 횟수는 현재 재료로 가능한 범위(최대16회)이며 산출 개수와 구분합니다. 입력 전달 자체가 올바른 선택을 보장하지는 않습니다.

## 검증과 다음 단계

전체573개 모의검증과 타입 검사를 통과했습니다. 행동별 인자 범위·철회 후보 연결·초기 계획의 두 응답 순서·관측된 공격 대상 연결을 포함합니다. 같은 저장 입력6회 비교에서 인자 철회는 기존5회, 범위 정보 추가3회, 철회 피드백까지 추가3회였습니다. 작은 재생 표본이며 피드백의 독립 효과나 실제 공백 감소를 입증하지 않습니다.

후속 공격 중단 분석에서는 완료된 절차가 현재 감독 역할을 계속 활성화하는 문제를 수정했습니다. 이전 중단12장면을 각2회 API 재생했을 때 `stop`은 기존23/24회, 수정12/24회였습니다. 수정안의 공격 선택12회 중11회는 같은 대상을 선택했고1회는 인자 철회였습니다. 가까운 대상에서도 중단은 남았습니다. 아래 서버 검증에서 실제 전달과 진행을 확인했습니다. 진행 중 제작의 늦은 계획 응답은 요청 시점의 사실과 이후 완료 근거를 분리합니다.
